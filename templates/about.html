About the Project

Problem statement

Households receive electricity bills but rarely understand when and why they use the most energy, and cannot anticipate future consumption. A data-driven tool is needed to analyse historical usage and forecast what comes next.

Existing system

Meters and bills show only totals for a billing period. Manual comparison is slow, hides daily and hourly patterns, and gives no forecast or personalised advice.

Proposed system

A Flask web application that cleans uploaded consumption data, analyses patterns, trains a Random Forest Regressor, forecasts future usage, evaluates the model and produces evidence-based recommendations.

Research gap

Many forecasting studies stop at a notebook. Few offer an easy end-to-end tool for non-experts that combines preprocessing, leakage-free validation, forecasting and advice in one place.

Objectives

  • Analyse historical household electricity consumption and identify high-consumption periods.
  • Forecast future consumption using a Random Forest Regressor.
  • Evaluate the model with MAE, MSE, RMSE and R².
  • Provide practical energy-saving recommendations based on the analysis.

Methodology

  • Preprocessing: date conversion, sorting, duplicate removal, invalid/missing value handling, outlier capping, regular time grid.
  • Features: year, month, day, weekday, weekend flag, hour, cyclical hour, lags and rolling means (past data only).
  • Split: chronological — oldest data for training, newest for testing.
  • Forecast: recursive multi-step prediction, each prediction becomes history for the next step.

Technologies used

  • Python 3 · Flask (backend)
  • Pandas, NumPy (data handling)
  • Scikit-learn (Random Forest, metrics) · Joblib (model saving)
  • HTML, CSS, JavaScript · Chart.js (charts)

Algorithm

Random Forest Regressor — averages many decision trees trained on bootstrap samples with random feature subsets, reducing over-fitting compared with a single tree.

Advantages

  • End-to-end, easy to use
  • No data leakage
  • Works with hourly or daily data
  • Transparent, evidence-based advice

Limitations

  • Uses only past consumption and calendar features (no weather or tariff data)
  • Long recursive forecasts become less accurate
  • Needs at least 3 weeks of hourly or 90 days of daily data
  • Single-user local application

Future enhancements

  • Weather and holiday features
  • Compare with other models (XGBoost, LSTM)
  • User accounts and database storage
  • Appliance-level analysis and cost estimates
